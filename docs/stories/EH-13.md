# EH-13 stories — Multi-source provenance and reversible imports

Owning feature: `docs/tasks/EH-13.md`. These leaves change public reusable behavior only; real archive content and private deployment values are forbidden.

## EH-13-01 — Record the multi-source observation and materialization ADR

- **Goal:** Settle the schema-neutral contract that later migrations and import services must implement.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Current rows store first/last-seen snapshot metadata but cannot explain or exclude every contributing import. Immutable observations and materialized presentation state must remain distinct.
- **Work to do:** Add an ADR defining owned accounts, source conversations, unified conversations, typed observation ownership, eligibility/exclusion, deterministic rematerialization, revoke/delete tombstones, soft deletion, and live-only-to-backup-confirmed transitions; include invariants and migration consequences.
- **Acceptance criteria:** The ADR states authoritative versus derived fields; defines identity keys across account/source/live/backup inputs; forbids fuzzy automatic merge and destructive exclusion; specifies deterministic conflict precedence and audit fields.
- **Verification:** Review every EH-13 criterion against the ADR; add an executable contract fixture or schema examples that fail if required identity inputs are omitted.
- **Out of scope:** Prisma migration, importer changes, UI, live integration, or real data.
- **Blocked by:** None.
- **Priority:** Urgent.
- **Model class:** Reasoning — this is the single load-bearing identity/materialization decision; later leaves consume it without redesign.

## EH-13-02 — Add owned-account and import-scope persistence

- **Goal:** Make the receiving WhatsApp account explicit on every source, snapshot, and import job.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Account identifiers are sensitive provenance; display labels are owner-controlled and cannot be stable identity. Follow EH-13-01.
- **Work to do:** Add the owned-account schema/migration and archive-scoped persistence port; bind Source, Snapshot, and ImportJob through enforced same-archive relations; migrate existing synthetic rows to an explicit legacy/default account without a production phone-number constant.
- **Acceptance criteria:** Two accounts may reuse source keys without collision; cross-archive/account bindings fail; every new import requires an account; account identity/display metadata is not exposed to MCP unless an existing bounded view explicitly requests safe provenance.
- **Verification:** Prisma validation plus PostgreSQL migration/constraint tests for two archives and two accounts.
- **Out of scope:** Source conversations, observations, pairing, account UI, or live sync.
- **Blocked by:** EH-13-01.
- **Priority:** Urgent.
- **Model class:** Medium.
## EH-13-03 — Separate source conversations from unified presentation conversations

- **Goal:** Preserve each account-specific WhatsApp chat while creating a reversible grouping seam for V2.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** A source conversation is immutable evidence keyed by owned account plus WhatsApp chat identity. A unified conversation is an owner-managed presentation group and may initially contain one source conversation.
- **Work to do:** Add schema/migration and ports for source conversations and unified conversations; migrate current Conversation rows into one-to-one groups; update normalized relations without losing stable identifiers.
- **Acceptance criteria:** Matching Jacky-like names across accounts do not merge; every message resolves to one source conversation and one current unified group; grouping can later change without rewriting message provenance; archive isolation constraints remain enforced.
- **Verification:** PostgreSQL migration and constraint tests covering same JID on two accounts, group chats, and cross-archive denial.
- **Out of scope:** Merge commands/UI, merged reads, fuzzy suggestions, or live events.
- **Blocked by:** EH-13-01, EH-13-02.
- **Priority:** Urgent.
- **Model class:** Medium.

## EH-13-04 — Persist typed import observations

- **Goal:** Record every eligible source/import contribution needed to explain and rematerialize normalized state.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Avoid an unconstrained polymorphic table with dangling entity IDs. Use typed relations or another ADR-compliant design that preserves database integrity.
- **Work to do:** Add observation persistence for conversations, messages/revisions/reactions, and attachment references; bind observations to archive, account, source, snapshot, import job, source identity, observed value digest, and observation time; expose bounded provenance reads through application ports.
- **Acceptance criteria:** Every imported normalized entity type in scope records its contributing import; replay upserts the same observation; two imports may support one materialized entity; cross-archive and dangling references fail at the database boundary.
- **Verification:** Migration tests plus PostgreSQL functional tests for replay, overlap, conflicting observations, and provenance enumeration.
- **Out of scope:** Rematerialization, UI provenance panels, live sidecars, or deletion events.
- **Blocked by:** EH-13-01, EH-13-02, EH-13-03.
- **Priority:** Urgent.
- **Model class:** Medium.

## EH-13-05 — Import account-scoped records through the observation ledger

- **Goal:** Make backup imports populate observations before deterministically updating normalized state.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Import completion and observation/materialized updates remain one atomic success boundary. Existing stable message behavior must continue across reordered snapshots.
- **Work to do:** Extend normalized adapter/import inputs with owned account and source-conversation identity; write typed observations; derive materialized rows using EH-13-01 precedence; keep replay and last-snapshot omission append-preserving.
- **Acceptance criteria:** Reimport changes neither logical rows nor observation count; two account sources with the same contact/JID remain distinct source conversations; overlapping backup observations share the correct logical message only when account/source identity permits; a failed transaction exposes no partial materialization.
- **Verification:** Focused unit tests and PostgreSQL functional tests extending the A/B/C permutation suite with two accounts and duplicate deliveries.
- **Out of scope:** Exclusion/rematerialization command, live event adapter, merge UI, or real backups.
- **Blocked by:** EH-13-04.
- **Priority:** Urgent.
- **Model class:** Medium.

## EH-13-06 — Exclude and re-enable one import deterministically

- **Goal:** Recover from a corrupt or wrongly classified import without deleting its evidence or harming overlapping valid imports.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Exclusion is an audited eligibility state, not deletion. The operation must be retry-safe and bounded to one archive; immutable Source and Snapshot artifacts are unchanged.
- **Work to do:** Add plan/apply application services for import exclusion and re-enable; compute affected materialized entities; rematerialize from remaining eligible observations transactionally or by recoverable bounded batches; record safe status and audit metadata.
- **Acceptance criteria:** Plan performs no mutation and reports bounded counts; apply removes only unsupported materialized values/entities; shared observations remain visible; re-enable recreates byte-for-byte equivalent normalized state; interruption is resumable and never marks an incomplete rebuild successful.
- **Verification:** Unit state-machine tests plus PostgreSQL functional tests for first/middle/last import exclusion, overlap, conflicting revisions, failure injection, retry, and re-enable.
- **Out of scope:** Deleting snapshot files, deleting observation rows, UI controls, or hard purge.
- **Blocked by:** EH-13-05.
- **Priority:** Urgent.
- **Model class:** Complex — deterministic recomputation and interruption safety are one irreducible consistency boundary.

## EH-13-07 — Preserve source revoke and deletion observations

- **Goal:** Represent WhatsApp deletion events and local soft deletion without erasing captured message content.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** A revoke/delete event may be observed after content, before content, or from only one source. Absence remains non-evidence. Source deletion and owner soft deletion are different fields.
- **Work to do:** Add append-preserving deletion observation/tombstone fields and import mapping; derive `sourceDeleted` status while retaining prior body/media; add owner-soft-delete columns required by V2 without exposing a user command yet.
- **Acceptance criteria:** Revoke-after-content preserves content and records when/source; revoke-before-content creates an explicit content-unavailable tombstone; later valid content may fill the tombstone without losing deletion history; owner soft-delete state cannot be set by a WhatsApp observation.
- **Verification:** Adapter unit fixtures and PostgreSQL functional tests for event order permutations, replay, overlap, and source-versus-owner state isolation.
- **Out of scope:** Live event transport, delete/restore UI, purge, or MCP policy.
- **Blocked by:** EH-13-04, EH-13-05.
- **Priority:** High.
- **Model class:** Medium.

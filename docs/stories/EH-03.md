# EH-03 stories — Snapshot intake and decryption

Owning feature: `docs/tasks/EH-03.md`. Only the leaf stories below are executable assignments.

## EH-03-01 — Define inbox and decryption application contracts

- **Goal:** Record the bounded types, state transitions, and ports for intake and decryption before filesystem/subprocess implementations.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** External Android sync ends at `/data/inbox/<delivery-id>`; encrypted inputs are immutable; plaintext is disposable; V1 has one worker replica.
- **Work to do:** Define delivery/snapshot/job value types and transition invariants; define filesystem, clock, hashing, lease, and decrypt ports; add transition unit tests.
- **Acceptance criteria:** Invalid state transitions fail deterministically; ports contain no WhatsApp SQLite or process-specific details; secret values are absent from domain/application types.
- **Verification:** Run unit tests, strict types, and architecture checks.
- **Out of scope:** Filesystem polling, manifests, subprocess execution, database persistence, and parsing.
- **Blocked by:** EH-02-05.
- **Priority:** High.
- **Model class:** Simple.

## EH-03-02 — Discover stable batches and claim them atomically

- **Goal:** Claim only quiet, unchanged inbox deliveries exactly once for one logical worker job.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Stability requires repeated size/mtime agreement over a configurable quiet period; arrivals after claim belong to a later batch.
- **Work to do:** Implement polling/stability evaluation; implement same-filesystem atomic claim or persisted lease according to the application contract; persist discovered/settling/claimed transitions.
- **Acceptance criteria:** Growing/changing batches remain unclaimed; two contenders yield one winner; post-claim arrivals are not folded into the claimed batch; source bytes/timestamps remain unchanged.
- **Verification:** Run filesystem/PostgreSQL functional tests with changing files, two contenders, and late arrivals.
- **Out of scope:** Hash manifests, decryption, parsing, and stale-lease recovery.
- **Blocked by:** EH-03-01.
- **Priority:** High.
- **Model class:** Medium.

## EH-03-03 — Create immutable snapshots and manifests

- **Goal:** Hash a claimed delivery into one immutable snapshot directory and allowlisted manifest without duplicate logical snapshots.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Manifest fields are limited to filenames, sizes, SHA-256, lifecycle times, adapter version when known, and sanitized outcome metadata.
- **Work to do:** Stream-hash claimed artifacts; atomically create snapshot directories/manifests; reconcile an already-completed source hash to the existing logical snapshot.
- **Acceptance criteria:** Snapshot files match recorded hashes; an identical source hash creates no second logical snapshot; partial writes are never treated as ready; inputs remain unchanged.
- **Verification:** Run functional tests for success, duplicate source, interrupted writes, hash mismatch, and retry.
- **Out of scope:** Decryption, SQLite validation, message import, and retention policy.
- **Blocked by:** EH-03-02.
- **Priority:** High.
- **Model class:** Medium.

## EH-03-04 — Implement the secret-safe wa-crypt-tools adapter

- **Goal:** Decrypt a snapshotted crypt15 database through a pinned bounded subprocess without exposing the key.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Use `wa-crypt-tools`; the key comes from a configured secret file and must not appear in argv, logs, manifests, PostgreSQL, or exceptions.
- **Work to do:** Verify and pin the compatible upstream invocation; implement timeout/resource/error bounds and secret delivery; validate output as read-only SQLite before returning it.
- **Acceptance criteria:** Valid synthetic input yields validated SQLite; invalid-key/corrupt/unsupported/timeout outcomes are classified and redacted; the sentinel key is absent from process listings and captured output.
- **Verification:** Run focused adapter tests, inspect argv/log captures for the sentinel, and validate output using SQLite read-only checks.
- **Out of scope:** Intake polling, snapshot manifests, parsing tables, production keys, and a Python network service.
- **Blocked by:** EH-03-01.
- **Priority:** High.
- **Model class:** Complex — upstream cryptography invocation and secret/process boundaries are one irreducible risk axis.

## EH-03-05 — Recover leases and clean disposable work

- **Goal:** Make decryption jobs retryable after handled failure or worker interruption while always cleaning plaintext work.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Immutable inputs remain; each job owns `/data/work/<job-id>`; diagnostics must be actionable but sanitized.
- **Work to do:** Implement lease heartbeat/expiry and stale-job recovery; implement per-job work creation/cleanup; map I/O, invalid-key, corruption, timeout, and internal errors to retryable/terminal states.
- **Acceptance criteria:** Stale work can be resumed or safely restarted once; plaintext is absent after success and handled failure; retries do not duplicate snapshots/jobs; diagnostics contain no secret content.
- **Verification:** Run functional crash/lease/retry tests and inspect work directories plus captured logs after each outcome.
- **Out of scope:** Message parsing, production scheduling, and snapshot retention.
- **Blocked by:** EH-03-02, EH-03-04.
- **Priority:** High.
- **Model class:** Medium.

## EH-03-06 — Verify the complete intake/decryption lifecycle

- **Goal:** Prove the composed worker lifecycle from stable inbox delivery through validated SQLite and cleanup.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** This story integrates already-defined components; it must fix only integration defects and must not redesign their contracts.
- **Work to do:** Add end-to-end synthetic lifecycle fixtures; cover duplicate delivery, failure/retry, stale lease, and clean success; document the worker verification command and sanitized outcomes.
- **Acceptance criteria:** One stable delivery reaches the expected terminal state exactly once; duplicate/reordered retries converge; all handled outcomes preserve immutable inputs and remove plaintext; unsupported output cannot be marked complete.
- **Verification:** Run the PostgreSQL/filesystem/subprocess functional lifecycle suite twice from clean state.
- **Out of scope:** WhatsApp table parsing, media import, production secrets, and deployment.
- **Blocked by:** EH-03-03, EH-03-05.
- **Priority:** High.
- **Model class:** Medium.

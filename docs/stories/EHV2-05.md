# EHV2-05 stories — Media galleries and recovery

Owning feature: `docs/tasks/EHV2-05.md`. Every filesystem input is hostile and bounded; recovery never changes the source directory/file.

## EHV2-05-01 — Add bounded gallery read contracts and indexes

- **Goal:** Query media by unified/source conversation, type, availability, date, and provenance with stable cursors.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** One attachment may link to several messages/chats and must appear once per requested gallery semantics. Privacy/deletion policy applies before pagination/counting.
- **Work to do:** Define gallery item/filter/cursor contracts; implement indexed PostgreSQL reads and safe metadata; document duplicate-link and cover ordering behavior.
- **Acceptance criteria:** Stable pagination has no skips/duplicates; policy-excluded media never affects rows/counts; available/missing/unsafe/unresolved/recovered states filter distinctly; queries meet a documented generated-scale target.
- **Verification:** PostgreSQL functional/query-plan tests and generated million-attachment benchmark slice.
- **Out of scope:** UI, thumbnails, recovery intake, transcription, or arbitrary paths.
- **Blocked by:** EH-13-08, EHV2-03-03, EHV2-04-02.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-05-02 — Build per-chat gallery and missing-media UX

- **Goal:** Provide a WhatsApp-like gallery for each unified conversation with clear unavailable-media explanations.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Reuse safe media delivery and design-system components. Never use an unavailable source path as a browser URL.
- **Work to do:** Add gallery tab/grid/list, type/date/availability filters, bounded loading, message-context navigation, and distinct missing/unsafe/unresolved/recovered states with accessible descriptions.
- **Acceptance criteria:** Gallery works on mobile/desktop/keyboard; selecting media opens safe preview or download and message context; missing items remain visible without broken-image requests; privacy/delete policy is preserved.
- **Verification:** Component tests and browser flows with large synthetic chats and every availability/MIME state.
- **Out of scope:** Global library, recovery controls, transcription, or new media codecs.
- **Blocked by:** EHV2-05-01.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-05-04 — Stage bounded recovery directories and uploads

- **Goal:** Hash possible replacement media from configured server recovery roots or owner uploads without exposing arbitrary filesystem access.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Directory roots are deployment configuration, not user-supplied arbitrary paths. Uploads use quarantine, size/count limits, safe filenames, MIME sniffing, and cleanup leases.
- **Work to do:** Add recovery-source/job contracts; implement allowlisted directory traversal without symlink escape and bounded upload staging; hash files into candidate metadata while leaving originals unchanged; sanitize status/errors.
- **Acceptance criteria:** Traversal/symlink/device/oversize/count-limit attacks fail; retries deduplicate candidates; source files remain unchanged; interrupted jobs recover/clean quarantine safely; no path/content leaks to logs/MCP.
- **Verification:** Filesystem/subprocess unit tests and functional fixtures for traversal, symlinks, duplicate bytes, interruption, upload limits, and cleanup.
- **Out of scope:** Candidate matching, CAS commit, private root configuration, or browser review.
- **Blocked by:** EHV2-05-01.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-05-05 — Rank recovery candidates and auto-link exact hashes

- **Goal:** Match lost-media candidates conservatively while allowing only exact content identity to attach automatically.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** SHA-256 equality is the sole automatic decision. Filename, size, dimensions, duration, timestamps, and chat context may rank suggestions but never decide.
- **Work to do:** Implement exact-hash matcher, deterministic metadata score/explanation, ambiguous/unmatched states, and immutable candidate-to-attachment proposal records.
- **Acceptance criteria:** Exact hash links all compatible references once; non-hash candidates remain pending owner review; ties are explicit; reruns are idempotent; unsafe MIME or contradictory hashes cannot link.
- **Verification:** Property/unit fixtures and PostgreSQL functional tests for exact, duplicate, ambiguous, collision/sentinel, and reordered candidate sets.
- **Out of scope:** Review UI, arbitrary fuzzy ML, CAS copy, or deleting candidates.
- **Blocked by:** EHV2-05-04.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-05-06 — Review and apply media recovery proposals

- **Goal:** Let the owner confirm/reject candidates and atomically place accepted bytes in CAS with durable provenance.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Applying re-hashes the staged file and rechecks attachment/job/version state. Rejecting is reversible as a review decision; it does not delete source bytes.
- **Work to do:** Add confirm/reject application commands, CAS atomic copy/linking, recovery observation/audit records, conflict handling, and browser proposal comparison/bulk exact-accept flows.
- **Acceptance criteria:** Stale/changed candidates refuse; accepted bytes hash correctly and become available/recovered; all linked messages update without duplicate Attachment rows; ambiguous proposals require explicit selection; audit retains source kind/digest without sensitive path exposure.
- **Verification:** CAS/PostgreSQL failure-injection tests and browser review tests for exact, ambiguous, stale, duplicate, cancel, and retry.
- **Out of scope:** Private deployment paths, transcript jobs, source deletion, or automatic fuzzy acceptance.
- **Blocked by:** EHV2-05-03, EHV2-05-05.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-05-07 — Deploy and accept gallery recovery boundaries

- **Goal:** Prove configured recovery roots, upload limits, gallery performance, and media recovery work privately without expanding file authority.
- **Repository:** `/home/matthijs/projects/unraided-treasures`
- **Context / constraints:** Configure only explicit read-only recovery roots and an isolated upload quarantine. Use synthetic/disposable media for apply proof; real-media inspection is owner-attended and unrecorded.
- **Work to do:** Add mounts/config/backup exclusions and health checks; deploy; exercise gallery policies, exact recovery, ambiguous review, restart/cleanup, denied paths, and CAS backup inclusion.
- **Acceptance criteria:** Only configured roots are readable; uploads and quarantine are bounded; recovery survives/retries correctly; CAS backup covers accepted bytes but not quarantine; gallery performance target holds; sanitized evidence contains no media/path/identity.
- **Verification:** Approved deployment/probes plus synthetic end-to-end recovery and negative path tests.
- **Out of scope:** Broad host mounts, Immich, real-data bulk recovery, transcription, or source cleanup.
- **Blocked by:** EHV2-05-06.
- **Priority:** Medium.
- **Model class:** Complex — private filesystem authority and end-to-end recovery are the isolated live risk.

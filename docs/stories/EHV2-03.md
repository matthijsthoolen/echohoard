# EHV2-03 stories — Hidden, locked, and MCP-private chats

Owning feature: `docs/tasks/EHV2-03.md`. EchoHoard policy is independent from any WhatsApp chat-lock observation.

## EHV2-03-01 — Define and persist the conversation privacy policy

- **Goal:** Establish independent UI visibility, lock, and MCP disclosure state with safe defaults.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Normal, hidden, and locked are presentation/auth states; MCP allow/deny is orthogonal. Existing chats migrate to normal plus MCP-allowed.
- **Work to do:** Add domain policy, schema/migration, audited update command, and archive-scoped port; retain optional source-lock metadata as non-authoritative provenance.
- **Acceptance criteria:** Every valid state combination is explicit; invalid transitions/cross-archive writes fail; defaults preserve V1 behavior; audit events contain IDs/actions only, not titles/content.
- **Verification:** Domain/unit tests and PostgreSQL migration/constraint/audit tests.
- **Out of scope:** Step-up authentication, UI filtering, MCP enforcement, or soft deletion.
- **Blocked by:** EH-13-08.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-03-02 — Implement recent Authentik step-up unlock sessions

- **Goal:** Require recent strong authentication before locked-chat content or metadata can be read.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Reuse Authentik/OIDC and durable server sessions; create no local PIN/password store. Unlock grants are short-lived, hashed/server-side, archive-scoped, revocable, and fail closed on uncertainty.
- **Work to do:** Define unlock challenge/callback/grant flow; implement recent-auth validation, expiry/revocation, and authorization context; add direct-route denial semantics.
- **Acceptance criteria:** Locked reads deny without a valid recent grant; grant is archive/session bound and expires; logout/revocation clears it globally; callback/replay/cross-archive attacks fail; tokens/claims are not logged.
- **Verification:** Unit OIDC/session tests and PostgreSQL functional tests for expiry, restart, replay, logout, and isolation.
- **Out of scope:** UI folder, MCP policy, custom secret code, or Authentik deployment changes.
- **Blocked by:** EHV2-03-01.
- **Priority:** High.
- **Model class:** Complex — step-up OIDC and durable authorization form one security boundary.

## EHV2-03-03 — Filter hidden and locked chats across UI reads

- **Goal:** Remove hidden/locked chats and derived data from ordinary UI reads while providing an authorized privacy folder.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Direct URLs, search, counts, galleries, people/timeline associations, previews, and errors must not reveal locked metadata before unlock.
- **Work to do:** Apply shared UI-purpose policy filters to conversation/detail/search/statistics/media services; add authorized hidden/locked listing modes; use non-enumerating denial behavior.
- **Acceptance criteria:** Ordinary reads contain no hidden/locked records or derived counts; hidden folder requires normal owner auth; locked folder/content additionally requires unlock grant; direct-ID behavior does not reveal existence; policy changes take effect immediately.
- **Verification:** Service/unit and PostgreSQL matrix tests across every read surface and state combination.
- **Out of scope:** Browser presentation, MCP, policy mutation, or soft deletion.
- **Blocked by:** EHV2-03-01, EHV2-03-02.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-03-04 — Build privacy settings and locked-folder UX

- **Goal:** Let the owner hide, lock, unhide, unlock, and configure MCP visibility clearly.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** Explain that EchoHoard privacy does not change WhatsApp. Use step-up Authentik flow and accessible design-system components.
- **Work to do:** Add chat privacy actions/settings; hidden and locked folders; recent-auth prompt, expiry behavior, and relock; independent MCP toggle with impact copy.
- **Acceptance criteria:** All policy combinations can be managed intentionally; locked metadata stays concealed before step-up; back/refresh/expiry relock safely; keyboard/mobile/screen-reader flows work; errors never fall back to exposing the chat.
- **Verification:** Component tests and browser scenarios for hide/lock/MCP toggle, denial, expiry, logout, and responsive navigation.
- **Out of scope:** New password/PIN, WhatsApp chat-lock mutation, deletion, or multi-user sharing.
- **Blocked by:** EHV2-03-02, EHV2-03-03.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-03-05 — Enforce per-chat MCP visibility

- **Goal:** Guarantee MCP-denied conversations and all derived records are absent from every tool and aggregate.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** UI unlock never grants MCP access. MCP purpose is explicit in application authorization; handlers cannot post-filter incomplete results.
- **Work to do:** Add MCP-purpose policy to shared reads; filter direct/list/search/person/media/timeline/status/statistics paths; produce non-enumerating results and safe aggregate counts.
- **Acceptance criteria:** Denied chat content, metadata, participants, attachments, snippets, counts, and existence are absent; direct IDs do not distinguish denied from missing; allowed chats remain functional; no tool can override the purpose.
- **Verification:** Complete MCP tool matrix with mixed policies, hostile content, direct IDs, search, pagination, and count tests.
- **Out of scope:** UI lock grants, MCP mutation, or transport authentication changes.
- **Blocked by:** EHV2-03-01, EHV2-02-05.
- **Priority:** High.
- **Model class:** Medium.

## EHV2-03-06 — Prove privacy policy composition end to end

- **Goal:** Verify unified chats, live messages, search, media, statistics, and MCP cannot bypass privacy.
- **Repository:** `/home/matthijs/projects/echohoard`
- **Context / constraints:** A unified conversation uses the most restrictive applicable policy until the owner explicitly changes the group policy; record this rule in the feature contract.
- **Work to do:** Add generated mixed-policy corpus and browser/MCP integration suite; exercise merge/unmerge, live arrival, policy changes, session expiry, and pagination cache behavior.
- **Acceptance criteria:** No leakage appears in UI HTML/JSON, caches, MCP, counts, errors, or logs; restrictive policy survives merge/live arrivals; unlock is never reused by MCP; suite passes after process restart.
- **Verification:** Run full unit/functional/browser/MCP suites with sentinel content and scan all captured outputs.
- **Out of scope:** Private deployment, soft-delete, purge, or performance tuning beyond regressions.
- **Blocked by:** EHV2-03-04, EHV2-03-05, EHV2-02-03.
- **Priority:** High.
- **Model class:** Medium.
